# ADR-020 — isolated public no-effect sandbox (APPROVED ARCHITECTURE)

**Status:** APPROVED ARCHITECTURE for the synthetic-only, no-protected-effect public sandbox by the owner's explicit Task 10D decision (2026-10-15), after comparison with canonical S5 §§3–8 and ADR-006/019. This does **not** approve public deployment, paid infrastructure, protected effects, or unrestricted hosted inference. A separate Task 10D local SC-01 Groq smoke is authorized only after exact Free-tier/nonbillable account and model gates are verified, with at most six generations and ₹0 paid charges. ADR-006 Option I-A, ADR-019 quotation binding, PRD-SEC001–020 and Task 04F recovery limits remain unchanged. The later Task 10B/10C sections below are historical implementation notes written before this approval; their activation blockers still apply.

## Conflict and decision needed

The canonical S5 architecture supports a known Windows-local application and excludes a remotely exposed public runtime. The repository's security and API contracts prohibit casually adding a public trust boundary or material API/schema incompatibility. Serving the local FastAPI/SQLite protected writer or Ollama directly would expose authority, resource effects and a Windows-only recovery assumption to untrusted internet traffic. The conservative fallback is **no public API, no LIVE activation, and no public sandbox**. A public-sandbox contract needs explicit architecture/security approval.

## Proposed new domain, not a protected operation

```
Vercel static showcase (visitor UI)
  -> separate public sandbox API (synthetic, no-effect capability)
      -> isolated visitor run store + bounded A/B read-only runner
      -> separately approved hosted model transport (future)

Windows-local protected resource / API-108 / API-109 / approvals / queue / recovery
  [no route, credential, volume, network path or import from public deployment]
```

The public demo's `GUIDED` and `CUSTOM` are **sandbox interaction modes**, not new protected operation classes or resource outcomes. A visitor may select a predefined scenario and supply bounded untrusted ticket text for one trusted fixture. The visitor cannot set grant, role, customer, account, order ownership, verified contact, approval, provider endpoint/tool, model prompt, fixture epoch or protected material. The sandbox's eligibility decision and B proposal are observations only. Even `ALLOW` yields **no resource attempt or communication**. H1/H2 come from server-owned synthetic records; H3/H4 remain lower trust. Only `read_assigned_ticket` and `read_verified_order_status` may be model-exposed. Exact quotation presence remains necessary, not proof of current human intent.

## Proposed browser/session and evidence contract

- Server creates an opaque high-entropy session secret, stores only its hash, sets an HttpOnly SameSite cookie and issues a separate CSRF token for same-origin mutations. No client-supplied principal or episode ID becomes authority. Every run/evidence read checks server-side ownership and expiry. A wrong owner receives the same not-found response as an absent run.
- Run submission requires a scoped idempotency key; the same key/same body returns the original run, and the same key/different body conflicts. Browser refresh performs a read only. A timed-out generation must not silently retry under a new key.
- Expose only allowlisted status, sanitized invocation stages, actual tool names/owners and observation/continuation flags, model-selected quotation versus trusted-derived span, H1–H4 **presence/compartment labels**, bounded proposal and safe failure code. Do not expose raw prompts, secrets, evaluator truth, free-form provider exception bodies or other visitors' source text.
- Custom tickets must be explicitly synthetic; size/format/URL and obvious contact-data checks are only safeguards, **not a guarantee against personally identifying submissions**. The final public policy must specify consent/warning, collection, encryption, retention window, access logs, backup handling and deletion jobs.

## Proposed quotas and failure rules

- Before **each** hosted request, a globally transactional or provider-enforced reservation must check project-wide daily generation/token/cost ceilings, per-run and per-session limits, concurrency and the global kill switch. Reserving only at run start is insufficient if the provider can bill beyond that bound. Do not treat provider free-tier marketing or a soft budget alert as a hard ₹0 ceiling.
- Enforce request bytes, maximum tool rounds, per-turn tokens, wall-clock duration, per-session/IP/bot abuse controls and trusted proxy attribution. Duplicate runs reuse their reservation. Expired/cancelled/failed runs retain safe terminal evidence only for the declared window. A late provider response after cancellation is never silently shown as a completed action.
- Provider timeout, 429, schema refusal, invalid quotation, missing B tool observation, shutdown, capacity exhaustion and uncertain storage commit have separate truthful states. None becomes `EXPLICIT_POLICY_DENIAL` or a protected resource receipt. Fail closed on lost shared budget state, provider entitlement or a storage outage.

## Local Task 10A evidence and nonportable limits

The Task 10A prototype at `src/scoperelay/sandbox/` is **loopback-only and OFF by default**. It uses a single-host SQLite metadata store, per-run synthetic DB, 30-minute session/run expiry with request/startup-triggered cleanup, five runs per session, two active runs, 40 reserved scripted-turn slots per UTC day, server-side CSRF/idempotency, and an operator-only local kill switch. It reuses the approved `ReadOnlyAgentRunner` with deterministic test doubles. New sandbox fixture DBs contain no evaluator truth rows and no protected effects. It contains no provider key or hosted request path.

These are not public-hosting guarantees. The run DB currently uses the canonical migration schema, including **empty reserved protected tables**; absence of HTTP routes and imports is code separation, not an OS/process capability boundary. A final public runtime should provision a minimal read-only-agent data schema or separate storage role that cannot write/open protected resource tables, and must have no access to the existing protected Windows database. The local SQLite budget is not a distributed quota across serverless instances. Cleanup is lazy and a crashed `RUNNING` row is conservatively retained; hard retention and crash recovery need a shared backend/job design. Obvious PII filtering is not complete privacy protection. The existing `ProviderAdapter` has an offline-prepared Groq final-turn shape, but no account or model smoke confirms it.

## Hosted topology proposed for review

Keep Vercel as the separately reviewed static frontend only. Host the sandbox API on a distinct service/process with a durable transactional shared session, run and budget store and no protected writer credentials, mounts or network access. The server—not Vercel browser JavaScript—holds provider credentials and fixed model/tool configuration. Transport should be HTTPS with explicit allowed origin and CSRF/session design; no wildcard CORS or spoofable forwarded-IP trust. The provider/model must be selected only after account-specific free or approved capped billing, data processing, model/tool/JSON compatibility, public visitor rights and safe abuse controls are verified. A paid database or compute service requires separate authorization. Vercel's incident project remains paused until an approved, independently checked deployment plan exists.

## Negative acceptance before approval/activation

Demonstrate cross-visitor evidence denial, forged `MANAGER`/`SYSTEM` text unable to mutate grants, wrong-order/contact denial, wrong/duplicate citation rejection, unknown or extra tool rejection, missing B observation, replay/conflicting idempotency, expired session, CSRF/Origin/Host controls, malformed/oversize input, injected HTML inertness, no evaluator truth in A/B messages, budget exhaustion and kill-switch rejection, provider timeout/429/invalid schema, no API-108/API-109 or approval route, zero resource attempts/effects/journals, and no model request while LIVE is disabled. Repeat in the chosen multi-instance hosting design; local tests alone do not prove it.

**Decision requested for Task 10B:** approve or reject this separate public no-effect domain, exact hosting/storage plan and exact provider/model/account/terms/budget. Only then consider a bounded hosted smoke. No production protected-action release is implied.

## Task 10B review delta — historical preapproval record

The preferred *candidate*, not an approved deployment, is **Option A: one controlled sandbox API instance on a persistent local volume**, separate from the Vercel static showcase and the Windows protected runtime. The existing SQLite state can serialize reservations across independent Python processes on the **same** host/file; Task 10B tests that property. It does not establish multi-host, serverless-disk or network-filesystem safety. Enforce exactly one deployed application instance/process for the first controlled experiment, with monitored restart and retained volume. A hosting vendor, free-tier eligibility, persistent-volume durability, backup/deletion policy, abuse edge and actual cost have not been selected. **Option B** (stateless workers plus a transactional managed store) is a later scale path requiring an approved store, atomic reservation implementation and cross-instance tests; do not configure it by switching a URL.

Local implementation now has a separate `LocalSandboxState` boundary, transactionally capped session creation (100/day, 20 active), five runs/session, two custom and two challenge runs/session, two concurrent runs and four reserved scripted turns/run within 40/day. Reservations are never refunded on timeout or crash. The session TTL can be configured up to 30 minutes; periodic background cleanup supplements startup/request cleanup. A failed file deletion retains database ownership metadata for retry. Expired credentials lose access even when a crashed `RUNNING` row conservatively remains. The browser holds CSRF only in memory and refreshes it from its HttpOnly-cookie session on reload; evidence remains owner-scoped. These are **local offline controls**, not a globally enforceable hosted-model charge ceiling or a complete hard-retention system.

**Approval delta before any public or hosted inference:** specify the exact vendor/region, one-instance enforcement and persistent-volume guarantee (or instead an Option B transactional store); HTTPS/Secure-cookie/origin/CSRF and trusted proxy/IP rate limits; human/bot verification if used; absolute provider-generation/token/concurrency budgets reserved before each call and reconciled after only authoritative evidence; explicit crash/cancellation semantics; a bounded retention job for stuck `RUNNING` rows and backups/logs; privacy notice and accidental-personal-data handling; provider/model/account free-or-paid entitlement and terms; secret management; observability and operator kill-switch/restart; end-to-end no-effect isolation proof. The canonical API-108/109, two protected operations, seven outcomes, ADR-006/019 and coherent-rollback limitation remain unchanged. Until reviewed, the local CLI stays loopback-only and LIVE is disabled.

## Task 10C offline implementation note — historical preapproval record

The local CLI now holds a single-host OS lease before startup reconciliation. Once exclusive ownership is established, a stale `RUNNING` run becomes sandbox-lifecycle `INTERRUPTED` with `WORKER_INTERRUPTED`; its reserved offline turns remain spent because a crashed worker's provider activity cannot be inferred from silence. Expired terminal files can then be removed at startup or by periodic cleanup. A second CLI instance with the same data directory is refused. Direct in-process test apps can still share the same file to prove SQLite atomicity; that is not a supported public multi-instance topology. Access expiry is immediate at the server check, but physical deletion can be delayed while the backend is down, file deletion fails, or a writer has not been safely reconciled. No hard public retention SLA is proposed without an independent storage/deletion guarantee.

The first-release source package is a repository checkout plus locked dependencies and an operator-supplied persistent data directory outside the checkout; it is not a standalone wheel or public container. It binds loopback only. The existing provider adapter has offline-tested, separate native-tool and best-effort JSON-schema final turns for Groq A/B; the current canonical union schemas are not proven compatible with Groq `strict=true`, and no account entitlement or ₹0 paid-charge guarantee is known. This note does **not** approve ADR-020, paid or free hosted requests, remote deployment or a protected effect.
